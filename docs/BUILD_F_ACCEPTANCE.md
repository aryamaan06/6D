# Build F acceptance — protected hosting preparation

Recorded October 25, 2026 before implementation completion. The user authorized Build F after confirming that Nebius AI Cloud billing was not configured. This milestone prepares and tests hosting locally. It does not authorize a cloud resource, card payment, public deployment or new provider spend.

- Preserve the existing localhost application, owner projects, records, remembered connections and provider spending ledger. A separate hosted entry point must not turn the existing owner server into a public server merely by changing its bind address.
- Require an explicit configured origin and a server-owned invitation secret for hosted access. Use HTTPS in deployment; allow insecure HTTP only through an explicit loopback-only test/development setting. Check exact Host and Origin and do not trust arbitrary forwarded headers.
- Give each authenticated browser session its own persistent project/runtime directory. Generate opaque unpredictable session tokens, retain token hashes rather than raw cookies, use HttpOnly/SameSite cookies and Secure for HTTPS, bound expiry and allocation, and preserve existing sessions/workspaces across restart.
- Seed only a public constructed rocket reference into each new review workspace. Do not copy the founder's database, credentials, private project inputs, logs or history. Retained workspaces must not silently recalculate historical reviews on restart.
- Reject visitor access to owner key connection/remembering, shutdown, qualification/evaluation/diagnostic, research search and metrics upload routes. Restrict ordinary engineering POSTs to an explicit allowlist. Projects, revisions, receipts and investigations from another session must remain inaccessible even when their IDs are known.
- Keep keys/configuration server-side outside public assets and the container image. Live AI is disabled by default. Enabling it requires an explicitly reviewed provider configuration, separately mounted key and persistent cumulative/day/session reservation caps. Errors, timeouts, logout or a fresh session cannot refund or reset retained spend.
- Rate-bound login attempts and session reads/writes, bound total session allocation and per-workspace data size, reject malformed/oversized inputs and expose controlled errors. Do not imply that this protects against every denial-of-service or establishes production SaaS security.
- Provide accessible invitation login, a visible hosted-session banner and sign-out, and remove unavailable administrative/provider controls from hosted views. Local-mode controls remain intact. No invitation secret/API key may enter query strings, browser storage or status/error bodies.
- Package a CPU application behind an HTTPS reverse proxy with persistent state, no publicly mapped application port, a non-root read-only application container and an explicit build-context allowlist. Credentials, private databases, Git metadata, work logs and personal files stay outside the image.
- Run independent local browser sessions through authentication, isolation, normal engineering changes, exports, expiry/logout, restart, error/route/origin controls and no-provider-call defaults. Preserve exact scoped results and distinguish mocked/offline checks from real provider calls and native Linux/container qualification.
- Before actual deployment, review the selected provider, persistent storage, resource estimate, operational and inference spending ceilings, public hostname/TLS and a judge-access plan. A Dockerfile or successful local server is not evidence of a hosted working URL.
- Document results and pending deployment explicitly, privacy-check the publication set, commit/push completed preparation and verify the remote commit. Do not label F public hosting complete while deployment is pending.

UI polishing, owner-led walkthrough, external user validation, current-build live AI qualification and final submission packaging remain separately acknowledged work. No new G/H functional scope is introduced.
